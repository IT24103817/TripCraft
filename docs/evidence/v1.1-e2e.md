These runs used a local stack built from branch `feat/v1.1-workflow`:
- the API, on a fresh `tripcraft_v11` database with migrations applied;
- the agent service on Ollama `llama3.1:8b`;
- React on Vite.

## API flow with the real agents (trip starting today)

```
1 submit (cities Kandy, Ella)      201 Submitted
2 start planning                   202 Planning
3 agents finished                  200 PendingReview
4 review: workflow                 200 PendingApproval (valid proposal, quotation v1)
5 manager sends to client          200 QuotationSent
6 tourist notification             200 ['QuotationSent']
7 tourist accepts                  200 ClientAccepted
8 manager confirms                 200 Confirmed holds=6
9 vouchers                         200 ['Trip', 'HotelNight' x4]
10 vouchers.pdf                    200 %PDF- (saved as sample-voucher.pdf)
11 guide scans trip voucher        200 Bahirawakanda Vihara Buddha Statue → InProgress (Voucher)

Trip history (actor, from → to: reason)
   Tourist            Submitted → Planning: Planning started.
   System             Planning → PendingReview: Proposal ready for review.
   OperationsManager  PendingReview → QuotationSent: Quotation v1 sent to the client.
   Tourist            QuotationSent → ClientAccepted: The client accepted quotation v1.
   OperationsManager  ClientAccepted → Confirmed: Confirmed: 6 holds placed and 5 vouchers issued.
   Guide              Confirmed → InProgress: First check-in at Bahirawakanda Vihara Buddha Statue.
```

The first try of step 11 found a real bug. The server compared the voucher day with the UTC date (1 Oct), while it
was already 2 Oct in Sri Lanka. "Today" now uses `OPERATOR_TIME_ZONE` (default Asia/Colombo), with a test, and
the scan above passed after that fix.

## Quotations go straight to the client (2 Oct 2026)

The lifecycle change "quotations go straight to the client; the operator confirms after acceptance" was run on the
full local stack: the API with the `QuotationsGoStraightToClient` migration applied to `tripcraft_v11`, the agents on
Ollama `llama3.1:8b`, React on Vite and the Flutter app on the Android emulator (`API_URL=http://10.0.2.2:5081`).
The migration turned the 6 old PendingReview trips and the 1 FailedSafely trip into NeedsOperator.

### Emulator run 1: everything from the phone (screenshots in `v1.1-autosend/run1-*`)

| Step | Result |
|------|--------|
| tourist1 fills **New trip** (Kandy → Ella, 23–26 Nov 2026, 2 travellers, USD 1,500, English guide, camera photo) → Submit | 201, trip Planning; the timeline shows the 7 steps |
| Agents: Planner → Itinerary → Resources → Validation | proposal valid; **no manager action** |
| Auto-send | trip **QuotationSent**, history actor **System** ("Quotation sent to the client automatically."), quotation v1 USD 281.93 sent, phone notification "Your quotation is ready", email "Your TripCraft quotation is ready" |
| Phone: **Accept quotation** | trip ClientAccepted; toast "Quotation accepted. The operator will now confirm your trip." |
| React as manager1: dashboard → Accepted trips → trip → **Next step: Accepted — confirm to book** → Confirm | "Trip confirmed: 5 holds created"; trip Confirmed; 4 vouchers (trip + 3 hotel nights); email "Your TripCraft trip is confirmed" |
| Phone: **Vouchers** tab | the trip voucher and the hotel-night QR codes (after a pull-to-refresh, see below) |

```
13:10:50  Submitted → Planning         Planning started.
13:12:24  Planning → QuotationSent      Quotation sent to the client automatically.
13:13:02  QuotationSent → ClientAccepted The client accepted quotation v1.
13:13:20  ClientAccepted → Confirmed    Confirmed: 5 holds placed and 4 vouchers issued.
```

**Found and fixed during the run.** The phone kept showing "No vouchers yet" after Confirm until the trip was pulled
down. The open trip screen reloaded only when the agent workflow status changed, and the notification poller showed
"Your trip is confirmed" without telling the trip screen. The same gap would hide an "Edit & resend" quote. Now the
shell reloads a trip (status, quote, vouchers, history) whenever the poller brings a new notification for it
(`tripsWithNewNotifications`, tested in `notifications_poller_test.dart`).

### Emulator run 2: the fix, with no touch on the phone (`v1.1-autosend/run2-*`)

The trip (Kandy → Ella, 11–14 Jan 2027) was submitted through the API, with the phone open on it. The phone moved
from Planning to **Quotation sent** by itself. Then Accept on the phone, the Vouchers tab ("No vouchers yet"), and
Confirm in React. **28 s later** the phone showed "Your trip is confirmed" and the QR vouchers, with no
pull-to-refresh (5 holds, 4 vouchers).

## Reconciliation check (2 Oct 2026)

The component-folder refactor and the direct-to-client lifecycle were checked together:
- **Components:** each of the 20 shared components has its own folder with `.tsx`, `.types.ts` and `index.ts`, and
  the barrel exports all 20. No flat component files. The Toast's `bg-white/20` and `bg-white/15` overlays became
  tone tokens (`bg-green-800` / `bg-red-800`), so `web/src` has no `bg-white`.
- **Restored features:** guide schedule search (`guide_home_test.dart` "schedule search"), the Trips page
  Quotations tab with the minimum-total filter (`TripQuotationsList.test.tsx`), and the passport prompt in the Book
  sheet (`book_package_photo_test.dart`) are all present and pass.
- **Statuses:** RevisionRequested was retired as an agent-workflow and a quotation status. Replan with note now sets
  the workflow to Planning, and the migration `RetireRevisionRequested` mapped the rows on `tripcraft_v11` (tried on
  a copy first): 5 workflows → FailedSafely (their trips were already NeedsOperator), 1 quotation → Superseded.
  The agents' verdict code (PLAN.md section 10) and old decision/audit labels are kept on purpose.
- **Dashboard tiles:** Accepted — confirm, Declined — needs a decision, Needs operator, Guide change requests,
  Cancellations.
- **k6 `agent-latency.js`:** now sends `cities` and measures the time until the quotation is sent.
- **Ollama runaway answers:** in two full Playwright runs, the demo trip failed safely because one Validation
  answer ran for 120 s (the Ollama log shows 2,540 tokens; normal answers are at most about 1,000). The agents now
  cap an Ollama answer at `OLLAMA_NUM_PREDICT=1536` tokens, so a runaway ends early and is repaired. The next full
  run passed 6/6 (6.0 min).
